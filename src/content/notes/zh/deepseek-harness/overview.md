## 为什么读 harness,而不是读 prompt

一个 agent 系统里,prompt 是最容易看到、也最容易被高估的部分。真正决定它能不能用的是外面那一圈:上下文怎么被组装、工具怎么被暴露、失败怎么被兜住、什么时候该停下来。这一圈就是 harness。

我想通过读一个真实的实现来回答:**harness 到底在承担哪些责任,以及这些责任为什么不能推给模型。**

## 这个系列想回答的问题

按我认为的依赖顺序排。后面的问题基本上要先答完前面的才有意义。

1. **边界**:一次 agent 调用的输入和输出到底是什么?谁负责维护状态?
2. **上下文**:上下文是怎么被组装的?超长的时候裁掉什么、保留什么、依据是什么?
3. **工具**:工具的 schema 是怎么定义的?调度、并发、结果回填怎么处理?
4. **失败**:工具报错、模型输出不合法、循环停不下来 —— 分别在哪一层被处理?
5. **终止**:凭什么判断"做完了"?这个判断是硬编码的还是模型自己决定的?
6. **评估**:改了 harness 之后,怎么知道是变好了而不是变坏了?

## 怎么读这个系列

- 每章开头有一个**版本锚点**,写明这章依据的是哪个 commit。这类代码变化快,没有锚点的笔记过几个月就不知道还成不成立。
- 每章结尾有一个**「还没搞懂的」**小节。那部分通常比结论更有信息量。
- 章节的 `萌芽 / 在长 / 稳定` 标记表示我自己对它的信心程度,不是完成度。
